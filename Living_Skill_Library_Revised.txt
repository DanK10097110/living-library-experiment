  What it tests
  This is a controlled comparison and small-model replication, not a new system. Verified
  code skills, outcome-driven updates and ALFWorld results are now well covered by 2026
  work. What this study adds is a faithful test of whether those findings hold with small
  local open models, against a strong trajectory-memory baseline, with every setting frozen
  in advance.

  The claim under test: a small open-source LLM agent that stores verified skills as code,
  and updates them from its successes and failures, becomes more reliable and cheaper
  over a stream of tasks than the same agent without that memory. Everything runs free on
  local open models, in about 10 weeks for one person.

  The bar to beat is not "no memory" but "memory of raw past attempts" given the same
  practice budget, because more experience helping is unsurprising.

  System
  Two local LLMs and a text simulator. Every check is free because it reads simulator state,
  and a failure goes up one level only when the level below can't fix it.




  system · 2 LLM levels, 3 checks, 1 library with an update gate

  Plans flow down the middle; failures climb the checks on the right. L1 sees only skill names
  and signatures; L2 sees full skill code and failure notes for the subgoal at hand. Every
  change to a skill, whether an in-episode repair or a new version, enters the library only
  through the update gate.


  The skill record, retrieval and updates
  Each skill is executable code with a typed contract, outcome counts, failure notes and
  regression tests:

       "id": "heat_and_place@v2",
       "parent": "heat_and_place@v1",
       "signature": "heat_and_place(obj, target)",
       "description": "Heat an object in the microwave, then put it in or on
     target.",
       "preconditions": ["findable(obj)", "exists(microwave)"],
       "postconditions": ["is_hot(obj)", "located(obj, target)"],
       "body": "python source calling simulator actions and other skills",
       "successes": 12,
       "failures": 3,
       "failure_notes": ["Open the microwave before putting the object in."],
       "tests": ["game_0193 start state", "game_0507 start state"],
       "embedding": "384 floats"
     }


  Pre- and postconditions come only from a fixed list of predicates the simulator can check,
  so the planner can't grade itself with vague conditions.

  Retrieval drops skills whose preconditions can't hold in the current state. It ranks the rest
  by description similarity plus a reliability score: a low percentile (10th, fixed at the freeze)
  of the Beta(1 + successes, 1 + failures) posterior. Unlike "success rate minus one standard
  deviation", this behaves sensibly after only 1–3 uses.


     Outcome                                                                               Update

     Postcondition holds                                                                   Success +1; save the start state as a test
                                                                                           (up to 10)

     Fails, preconditions held                                                             Failure +1; L2 writes a one-line failure note

     Fails, preconditions didn't hold                                                      No change to the skill; logged as a retrieval
                                                                                           error

     Posterior mean below 0.6 after 5 uses, or 3                                           L2 writes a new version
     failures in a row


  One gate for every change. SkillOps reports that external maintenance can conflict with
  agents repairing their own skills. Here, both in-episode repairs and scheduled new
  versions go through the same gate:

    1. A repair can be used immediately to finish the current episode, but is saved only as a
       candidate version.


                                                                                                                                      Page 5 of 14
Living Skill Library for Hierarchical Embodied Planning: Lean Proof of Concept (Revised)




    2. A candidate becomes active only if it passes every stored test of the version it
         replaces.
    3. The old version stays as a fallback. If the candidate's posterior mean falls below the old
         version's reliability score after 5 uses, the old version is restored.

  The append-only ablation (E−) skips every row except saving new skills. The text
  simulator re-runs tests in milliseconds, which makes the gate affordable.

  How E-text stays a fair comparison. E runs first and logs its library before each evaluation
  task. E-text then runs the same seed and task order, and before each task it sees exactly
  the library E had at that point. Each skill is rendered as text by a rule fixed at the freeze:
  description, conditions, the body as numbered steps, and failure notes. The L2 model acts
  step by step from that text. E-text's own outcomes update nothing, so the content is
  identical and no extra practice is needed.

  Evaluation runs on the 134 unseen games in a fixed order, with libraries still updating, so
  each run gives a learning curve. Seeds vary task order and sampling.

  H3 uses skill invocations rather than tasks as its primary unit. Each task calls several skills,
  so this gives hundreds of observations instead of 134, and it exists in both E and E−. Task
  success is still reported for H3, with the expectation that it will be underpowered.

  Secondary metrics:

        Task success for H3; tokens per task weighted input 1 : output 4, for comparison with
        EvoLib.
        Break-even task count: the evaluation task at which E's cumulative cost drops below
        D's, reported as SkillSmith does.
        Skill reuse rate, library size over time, false-success rate.
        How often each condition retrieves a skill below the reliability threshold (E vs E−).
        Descriptive, E only: per-skill success before and after repair; share of candidate
        versions that fail a regression test.

  GPU-seconds is primary for H2 because it is the real cost on local hardware. Weighted
  tokens reflect API pricing, and with prefix caching input tokens are much cheaper locally.

  Statistics: paired bootstrap 95% confidence intervals over the 134 tasks, averaging seeds
  per task. The invocation metric is bootstrapped by task, since invocations within a task
  are not independent. Holm correction across the four primary tests. Differences under
  roughly 10 points in task success won't be distinguishable, so say so instead of over-
  reading small gaps.

  Success criterion (fixed at the end of the pilot): E beats D by at least 10 points in task
  success, or matches it within the confidence interval at 30% lower amortized GPU-
  seconds; and E beats E− on skill-invocation success. H4 is reported but not part of the
  criterion. A negative result gets written up too.

  Possible extension: imagined practice (Dyna-style)
  This is optional, attempted only if the core study finishes with time to spare; nothing in
  the main design depends on it. The question: can skills drafted in imagined rollouts
  replace some real practice?

  Learning executable action rules from trajectories is not new. WALL-E and WALL-E 2.0 do
  this on ALFWorld, combined with an LLM. What this extension adds is two constraints: a
  capped real-practice budget, and the rule that imagined successes never count until
  verified for real.



                                                                                           Page 9 of 14
Living Skill Library for Hierarchical Embodied Planning: Lean Proof of Concept (Revised)




  The text simulator is already free, so imagining saves nothing unless real interaction is
  made scarce on purpose. The extension treats ALFWorld as the "real robot" with a capped
  practice budget and compares conditions at an equal number of real episodes.

    1. Learn a world model from logs. From every real step, record which predicates changed
       after each action type and what had to hold beforehand. ALFWorld is deterministic, so
       this table settles quickly into learned planning rules. Use the table rather than an LLM
        to track state.
    2. Imagine scenarios. Recombine objects and receptacles seen in real games into new
       start states and goals. Run L1 plans and L2 skills inside the learned model; each
       imagined success yields a draft skill.
    3. Distill. Group drafts that share postconditions and action-type sequences, keep the
       shortest per group, and merge versions differing in one argument into a parameterized
       skill.
    4. Verify before trusting. A distilled skill enters the library only after passing in the real
       simulator on at least two real scenarios. Imagined successes never count toward
       reliability.

  When a verified skill later fails for real, the action rule that misled it is corrected in the
  learned model, closing the Dyna loop.

  The extension fails if imagined practice doesn't beat the 250-real condition, or if more
  than half of distilled skills fail real verification. Capping imagination at about 1,000 L2
  drafts keeps it near the cost of 250 real episodes; check that estimate before committing.

  memory; a robot foundation-model executor; a knowledge graph or GNN; using an LLM as

  domains. Each is a follow-up worth doing only if this study shows a real effect.
